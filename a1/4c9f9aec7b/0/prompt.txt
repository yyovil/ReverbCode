**On HTTP to the Go daemon** — yes, and that's already the architecture in the PR. The renderer talks to the daemon three ways:

| Channel | Protocol | Used for |
|---|---|---|
| REST | HTTP → `http://127.0.0.1:&lt;port&gt;/api/v1/...` | CRUD — projects, sessions, tasks |
| CDC events | SSE (HTTP long-poll) → `/api/v1/events` | Live updates — session/PR state changes |
| Terminal PTY | WebSocket → `/mux` | Keystroke/output streaming |

All three go from Chromium (the renderer process) directly to the Go daemon over loopback — which is why the CORS middleware in PR #167 was necessary. The alternative would be routing everything through the Electron main process via IPC, but that would make SSE and WebSocket significantly messier to proxy, so direct HTTP is the right call here.

The one thing still unresolved from the architectural review: the renderer currently hardcodes port 3001. The daemon writes its actual bound port to `running.json`, and `daemon-discovery.ts` already parses that — it just isn't wired into `main.ts` yet to broadcast the port to the renderer at startup.
